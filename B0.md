# B0 — The `count` trap

## 1. Original behaviour

The original Terraform configuration used `count` to create one S3 bucket for each landlord account:

```hcl
resource "aws_s3_bucket" "landlord_media" {
  count  = length(var.landlord_accounts)
  bucket = "haven-media-${var.landlord_accounts[count.index]}"
}
## 2. Why this is dangerous

Terraform identifies `count` resources by their numeric addresses, such as:

`aws_s3_bucket.landlord_media[1]`

Removing a landlord from the middle changes which account each index represents. Terraform can therefore interpret an existing bucket as belonging to a different landlord and propose replacing it or destroying another bucket.

For a multi-tenant platform, this risks unintended infrastructure changes and potentially destructive operations against another landlord's media.

## 3. The fix

Use `for_each` with stable landlord account IDs as resource keys:

```hcl
resource "aws_s3_bucket" "landlord_media" {
  for_each = toset(var.landlord_accounts)

  bucket = "haven-media-${each.key}"

  tags = {
    landlord_account_id = each.key
  }
}

# Design Notes

## B2 — idempotency key

The cost-tag validator uses the Terraform resource `address` as its deduplication key.

For example, `aws_s3_bucket.listing_media` identifies one resource in the plan. The validator stores non-compliant addresses in a Python `set`, so repeated entries for the same address are reported only once.

The validator processes only resources whose planned actions are exactly `["create"]` or `["update"]`. It checks that the resulting `landlord_account_id` tag exists, is a string, and is not empty or whitespace.

The output is deterministic because:
- The same plan file supplies the same resource changes.
- The same action and tag checks are applied on every run.
- A set removes duplicate resource addresses.
- The final addresses are sorted before printing.
- The exit code is determined by whether the set of missing-tag addresses is empty.

This provides idempotency without persisting state between executions. Running the script twice against an unchanged plan file produces identical output and the same exit code.

The validator returns a non-zero exit code when non-compliant resources are found, making it suitable for CI/CD pipeline enforcement.

## B2 — screening report access boundary

The business authorization boundary is `landlord_account_id`, because a landlord account is the billing and ownership boundary in the supplied domain model.

The authorization function resolves the report's tenant and then the tenant's property. It permits access only when the property's landlord account matches the property manager's landlord account.

The function fails closed when:
- The report's tenant cannot be found.
- The tenant ID is ambiguous.
- The tenant's property cannot be found.
- The property ID is ambiguous.
- The manager does not have a matching non-empty landlord account ID.

This avoids relying on `tenant_id` or `property_id` as the authorization boundary. Those IDs identify records, but do not establish the manager's landlord-level authorization.

## B0 — stable Terraform resource identity

The original `count` implementation identified landlord buckets by list index. Removing a middle element shifted indexes and caused Terraform to propose unintended replacements and destruction.

The implementation uses `for_each` with landlord account IDs as keys. Explicit `moved` blocks map the four existing count-based state addresses to their new keyed addresses.

This preserves the existing resources during migration and ensures that removing one landlord account affects only that account's bucket.

The migration blocks cover the four existing seeded resources. If additional legacy count-based addresses exist in another state, their mappings must also be planned and verified before migration.

## B1 — storage lifecycle and deletion requirements

Glacier Flexible Retrieval has a 90-day minimum storage duration. Deleting an object after only 10 days in that class can incur a prorated charge for the remaining 80 days.

The redesign uses S3 Intelligent-Tiering for sold listing photos. It avoids the Glacier Flexible Retrieval minimum-duration penalty and supports automatic access-tier optimization. Optional asynchronous Archive Access and Deep Archive Access tiers are intentionally excluded because the workload has a seller deletion requirement.

The lifecycle rule filters for objects tagged `listing_status=sold`. The application must apply this tag when a listing is sold. The lifecycle transition's 30-day clock is measured from object creation, not from the time the tag is applied.

The application, rather than the lifecycle rule, owns the seller deletion SLA. Its deletion workflow must account for object versions, replicas, retention settings, and legal holds where applicable. Intelligent-Tiering monitoring and automation charges and lifecycle request costs must also be considered.
